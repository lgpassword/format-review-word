# Word 模板格式分析系统需求与设计文档

> 本文档是本项目后续开发的主文档。后续开发应直接依据本文档内容拆分 beads 任务、确定阶段边界、实现功能和执行验收。若需求发生变化，应先更新本文档，再进入程序开发。

## 1. 项目目标

本项目建设一个基于 ASP.NET Core 的 Web 系统，用于对 Word 文档进行模板符合性检查。

用户先上传一个带批注的 Word 模板文档，系统读取模板中的批注和格式规则；随后用户上传待检查的 Word 文档，系统将待检查文档与模板进行对比，输出格式问题报告，帮助用户发现字体、字号、段落间距、表格结构、异常大空白等不符合模板要求的地方。

## 2. 适用场景

- 公司内部公文、报告、投标文件、合同、方案书的格式审核。
- 教育或科研场景中论文、申报书、课程材料的模板检查。
- 需要统一排版规范，但人工检查成本较高的 Word 文档审查流程。

## 3. 用户流程

1. 用户打开系统首页。
2. 页面先只显示“上传模板文档”。
3. 用户上传模板 Word 文档。
4. 系统分析模板，读取模板中的批注、标题样式、正文样式、段落间距、页面设置、表格格式等信息。
5. 模板分析完成后，页面显示模板分析摘要。
6. 页面再显示“上传实际文档”。
7. 用户上传待检查 Word 文档。
8. 系统执行格式对比。
9. 页面展示检测报告，并提供带批注 Word 文档下载。
10. 用户根据报告和 Word 批注修改文档。

界面顺序必须明确：先上传模板并完成分析，再上传实际文档。不要在初始页面同时要求用户上传两个文件。

## 4. 文件要求

### 4.1 支持文件

- 支持 `.docx` 格式。
- 支持旧版 `.doc` 格式，上传后在服务端转换为 `.docx` 再分析。

### 4.2 文件大小

建议初版限制单个文件不超过 20 MB。后续可根据部署环境调整。

### 4.3 文件安全

- 上传文件只在服务端临时处理。
- 初版不永久保存上传文件。
- 分析完成后释放文件流。
- 后续如需历史报告，可再增加文件存储和数据库。

### 4.4 `.doc` 兼容方式

旧版 `.doc` 文件在服务端通过 Windows Word 自动化转换为 `.docx`，然后复用现有分析、对比、批注回写和 HTML 报告流程。

要求：

- 原始 `.doc` 文件保留，不覆盖。
- 转换失败时给出明确错误提示。
- 输出文件仍以 `.docx` 和 HTML 为主。
- 如果当前环境没有安装 Word，则 `.doc` 转换不可用，需提示用户改用 `.docx`。

## 5. 模板批注读取

模板文档中的批注用于补充人工规则说明，例如：

- “一级标题使用黑体三号”
- “正文首行缩进 2 字符”
- “表格标题居中”
- “本段前后不要留大空白”

系统需要读取以下批注信息：

- 批注作者
- 批注时间
- 批注内容
- 批注所在的上下文文本

初版重点展示批注内容和上下文，不强制把自然语言批注全部自动转换成规则。后续可以增加“批注规则解析器”，把固定格式批注转换为可执行规则。

### 5.1 多模板规则来源

系统应支持“总模板 + 已合格参考模板”的规则生成方式：

1. 用户先上传总模板。
2. 总模板分析完成后，用户可以继续上传一个或多个已经审核合格的参考模板。
3. 系统对比总模板和参考模板中的字体、字号、段落、表格、页眉页脚、目录、页码、对象等规则。
4. 如果总模板与参考模板出现偏差，页面弹出规则冲突对话框，让用户选择最终采用哪一条规则，也可以编辑规则内容。
5. 用户确认后的规则只作用于当前检测会话，用于后续文档检查和正常文档生成。
6. 规则冲突和用户选择应写入 HTML 报告，便于回查。

规则优先级：

1. 用户在冲突对话框中确认或编辑的规则。
2. 总模板批注中能识别的规则。
3. 总模板的 Word 样式和直接格式。
4. 已合格参考模板中稳定出现的规则。
5. 常见 Word 规则推断。

如果模板批注和样式继承结果冲突，优先按模板批注执行。无法识别的自然语言批注应原样展示，并标记为“需人工确认”。

## 6. 审查后样式参考

参考文档：

```text
C:\Users\liugang\Downloads\数字孪生校园系统的设计与实现_检测报告\数字孪生校园系统的设计与实现.docx
C:\Users\liugang\Downloads\数字孪生校园系统的设计与实现_检测报告\数字孪生校园系统的设计与实现_格式检测报告.html
```

这些文件是审查后的样式参考：一个是带批注的 Word 文档，一个是 HTML 格式检测报告。程序生成的审查结果可以参考它们的定位方式和报告结构，但必须比它们更容易让人看懂。

### 6.1 样例观察

样例文档中包含约 297 条批注，问题类型包括：

- 页面设置问题，例如页边距、页眉边距、页码样式。
- 字体问题，例如字体、字号、字形。
- 段落问题，例如行距、缩进、对齐方式、空白行。
- 目录问题，例如目录页码与实际页码不一致。
- 提醒类问题，例如英文标点后缺少半角空格。

样例 HTML 报告包含：

- 报告标题和报告编号。
- 检测说明。
- 检测结论。
- 问题总数。
- 是否达到合格标准。
- 按章节或类别分组的问题表格。
- 每条问题的严重级别和问题描述。

样例批注通常使用类似格式：

```text
1-11-封面-错误-中文和全角标点要求使用字体 宋体, 实际：黑体字号错误...
```

这种格式虽然包含位置和问题信息，但对普通用户不够友好，主要问题是：

- 内容挤在一行里，不容易阅读。
- 问题类型、模板要求、实际情况和修改建议没有清楚分层。
- 多个问题合在一起时，用户很难判断先改哪里。
- 缺少明确的操作建议。

### 6.2 改进目标

本系统生成的报告和 Word 批注必须做到：

- 保留样例中的页码、段落、模块等定位信息。
- 批注内容分行展示，避免长句堆在一起。
- 每条批注明确说明“哪里错了、要求是什么、现在是什么、怎么改”。
- 同一位置多个问题可以合并，但必须用编号分开。
- 严重问题优先显示，并在批注标题中体现严重级别。
- 页面报告和 Word 批注使用同一套问题编号，方便互相查找。
- HTML/页面报告应比样例更易筛选，至少支持按严重级别、问题类型、章节位置过滤。

## 7. 格式分析范围

### 7.1 字体与字号

检查项：

- 字体名称是否与模板一致。
- 字号是否与模板一致。
- 加粗、斜体、下划线是否异常。
- 中文字体和西文字体是否混用异常。

对比策略：

- 先按字符和文本运行提取实际字体、字号、加粗、斜体、下划线、中西文字体等信息。
- 同时解析直接格式和样式继承链：先看直接值，不足时追溯段落样式、字符样式、基础样式和文档默认值。
- 检查结果按字符/运行计算，但页面报告和 Word 批注按段落合并成用户能读懂的问题。
- 字号必须优先显示为 Word 用户熟悉的术语，例如“小初”“小二”“小三”“小四”；无法识别时再显示原始值。
- 字体名称优先显示 Word 字体名称，例如“楷体”“宋体”“黑体”；无法识别时再显示原始值。
- 禁止只显示 `24`、`72` 这类普通用户无法理解的内部数值。
- 不应轻易输出“未设置”。如果直接格式没有值，应继续查样式继承后的最终显示值。
- 与模板主规则、模板批注规则或用户确认规则不一致时记录问题。

### 7.2 段落格式

检查项：

- 段前间距。
- 段后间距。
- 行距。
- 对齐方式。
- 首行缩进。
- 左右缩进。
- 分页符、分节符使用情况。

对比策略：

- 以模板批注、用户确认规则、段落直接格式、样式继承后的最终值为综合基准。
- 检查段前、段后、行距、对齐、缩进、分页控制、分节符、分页符等字段。
- 页面和批注中优先使用 Word 对话框里的说法，例如“单倍行距”“固定值 18 磅”“居中对齐”“首行缩进 2 字符”。
- 无法转换成 Word 术语时，才显示原始值作为兜底。
- 同一段内存在多个来源或多个样式差异时，系统内部都要检查，最终按用户选择拆成多条 Word 批注。

### 7.3 标题层级

检查项：

- 标题样式是否正确。
- 标题字体和字号是否符合模板。
- 标题前后间距是否符合模板。
- 标题层级是否异常跳级。

初版可根据 Word 样式名、段落大纲级别、文本特征进行识别。

### 7.4 表格格式

检查项：

- 表格数量是否与模板预期接近。
- 表格列数是否异常。
- 表头行是否存在。
- 单元格边框是否缺失。
- 表格宽度、对齐方式是否异常。
- 表格内文字字体、字号、对齐方式是否异常。

对比策略：

- 提取模板表格的行列结构和常见格式。
- 对目标文档每个表格生成结构摘要。
- 发现列数、边框、单元格文本格式偏差时输出问题。
- 表格内文字也要按字符和运行检查字体、字号、对齐、段落间距。
- 表格列宽、行高、边框、表格对齐方式优先转换成 Word 用户能理解的说法。
- 正常文档生成时，只有当表格过长并产生分页问题时才自动拆成副表；短表或通过增减文字才能解决的问题不自动改，由用户处理。
- 长表拆成副表时沿用原表标题并增加“（续表）”，每页或每个续表重复表头。

### 7.5 页面设置

参考样例中页面设置问题占比较高，初版应纳入检测范围。

检查项：

- 上、下、左、右页边距。
- 页眉边距。
- 页脚边距。
- 纸张大小。
- 纸张方向。
- 分节后的页面设置是否前后一致。

对比策略：

- 读取模板的 `SectionProperties`。
- 读取待检查文档每一节的 `SectionProperties`。
- 对边距、纸张大小、方向等差异输出问题。

### 7.6 目录与页码

参考样例中存在目录页码与实际页码不一致的问题。初版可以先做基础检测，后续再增强。

初版检查项：

- 是否存在目录域。
- 目录项样式是否异常。
- 页码格式是否与模板一致。

增强检查项：

- 自动更新或解析目录页码。
- 对比目录页码和正文实际页码。

页码规则不能简单按第一页开始计算。系统应按模板规则识别封面、目录、正文等区域，支持“目录不计入正文页码”“正文从指定区域重新计页”等情况。页码规则来源为：

1. 模板批注。
2. 模板分节、页码、目录域等 Word 设置。

如果模板批注和分节设置都无法判断页码规则，则页码/目录部分不强行判断错误，只在页面报告、问题列表、HTML 报告和 Word 对应区域附近给出“未检查/无法判断”的清楚提示。

自动更新目录优先使用 Microsoft Word 更新域；如果运行环境没有可用 Word 能力，则正常报告继续生成，并将目录/页码标为未检查。

### 7.7 大空白检测

Word 的真实页面排版依赖 Word 渲染引擎，单纯读取 `.docx` XML 无法 100% 判断页面视觉空白。

初版采用结构化检测：

- 连续空段落数量过多。
- 段前或段后间距异常大。
- 连续分页符。
- 手动换行过多。
- 空表格或空单元格造成的空白。

后续增强方案：

- 检查图片、表格、分页符、分节符和大段空白共同造成的页面空白。
- 正常文档生成时，图片只有在造成页面空白问题时才自动调整。
- 图片调整必须保持原始宽高比，只缩放，不裁切，不改位置，不改环绕方式。
- 图片缩放应尽量保持同类图片尺寸一致，避免一个特别大、一个特别小。

## 8. 检测结果报告

报告应包含：

- 报告编号。
- 模板文件名。
- 待检查文件名。
- 检查时间。
- 检测依据。
- 检测结论。
- 模板批注列表。
- 模板格式摘要。
- 问题总数。
- 问题严重级别统计。
- 问题类型统计。
- 详细问题列表。
- 带批注 Word 文档下载入口。
- 每个区域的检查覆盖率。
- 未检查项和未检查原因。
- 后台任务进度和完成提示。

每条问题建议包含：

- 问题编号。
- 问题类型，例如字体、段落、表格、空白。
- 位置描述，例如第几个段落、第几个表格、第几行附近。
- 页面或章节位置。
- 模板要求。
- 实际情况。
- 修改建议。
- 严重级别。

严重级别建议：

- `Error`：明显不符合模板，必须修改。
- `Warning`：疑似问题，需要人工确认。
- `Info`：提示信息，不一定需要修改。

### 8.1 报告可读性要求

报告不能只输出机器化字符串，应使用普通用户能理解的表达。参考 HTML 报告中“检测说明、检测结论、问题列表”的结构，但页面交互和问题说明要更清楚。

推荐页面展示格式：

```text
问题 F-001：封面标题行距不符合模板
位置：第 1 页，第 5 段，封面标题
严重级别：错误
模板要求：单倍行距
实际情况：1.5 倍行距
修改建议：选中该标题，在“段落”设置中把行距改为“单倍行距”。
```

### 8.2 HTML/页面报告结构

系统分析完成后应在 Web 页面显示报告，并支持后续导出为独立 HTML 报告。初版页面不做复杂仪表盘，只保留用户完成审查所需的核心信息。

报告结构建议：

1. 报告头部
   - 报告编号。
   - 检查时间。
   - 模板文件名。
   - 待检查文件名。
   - 检测模板或检测依据。

2. 检测结论
   - 是否通过。
   - 问题总数。
   - 严重、错误、提醒数量。
   - 字体、段落、页面设置、表格、目录、大空白等分类统计。

3. 操作区
   - 下载带批注 Word 文档。
   - 导出 HTML 报告。
   - 后续可扩展为导出 Excel/CSV。

4. 问题筛选区
   - 初版只保留简单筛选。
   - 按严重级别筛选。
   - 按问题类型筛选。
   - 关键词搜索、章节筛选放到后续增强。

5. 问题列表
   - 问题编号。
   - 严重级别。
   - 位置。
   - 问题标题。
   - 模板要求。
   - 实际情况。
   - 修改建议。
   - 对应 Word 批注编号。

增强后还应支持：

- 按文档区域筛选：封面、摘要、目录、正文、参考文献、附录、表格、页眉页脚、其他。
- 按页码筛选，页码应尽量按模板页码规则计算。
- 按是否已自动修正、是否待确认筛选。
- 问题列表每页显示 100 条。
- 每个区域显示覆盖率。覆盖率按字符数、段落数和对象数统计。
- 对覆盖率低的区域进行红色高亮，并提示“该区域可能漏检”。
- 如果某个对象因技术限制无法完整检查，应计入未检查并说明原因。
- 对象数包含表格、图片、文本框、脚注、尾注、页眉页脚对象。

### 8.3 HTML 报告导出

初版 Web 页面直接展示检测报告。若实现成本允许，应提供“导出 HTML 报告”功能。

导出的 HTML 报告要求：

- 可以脱离系统单独打开。
- 保留检测说明、检测结论、统计信息和问题列表。
- 样式简洁清晰，便于打印或转 PDF。
- 不依赖外部网络资源。
- 与带批注 Word 文档使用同一套问题编号。
- 包含自动修正记录。
- 自动修正记录按文档区域分组，包含位置、修改项、修改前后、修改原因和模板规则摘要。

### 8.5 后台检查进度

大文档、逐字符检查和全对象检查可能耗时较长。系统应使用后台任务执行检查，页面显示：

- 总进度百分比。
- 当前正在检查的区域或对象。
- 已发现问题数。

任务完成后，页面自动刷新并弹出完成提示。

### 8.6 待确认规则

无法自动识别的模板批注或冲突规则，应在问题列表中标记“待确认”。用户可以点击问题打开规则编辑弹窗。

弹窗字段：

- 区域。
- 检查项。
- 当前值。
- 模板要求。
- 适用范围。
- 备注。

用户确认规则后，只重新检查相关区域，不重新检查整篇文档。手动确认规则只对当前检测有效，不进入长期模板库；检测结束后只保留在 HTML 报告中。

### 8.4 问题编号规则

问题编号建议按类型生成：

- `P-001`：页面设置问题。
- `F-001`：字体和字号问题。
- `S-001`：段落和行距问题。
- `T-001`：表格问题。
- `B-001`：大空白问题。
- `C-001`：目录和页码问题。
- `I-001`：提醒类问题。

页面报告和 Word 批注必须使用相同编号。

## 9. 原文档批注回写

当系统检测到格式问题时，除了在页面报告中展示问题，还需要在待检查 Word 文档的对应位置插入批注。用户应能下载一份“带问题批注的 Word 文档”，直接在 Word 中看到哪里需要修改。

### 9.1 输出文件

- 不直接覆盖用户上传的原文件。
- 系统生成一个新的 `.docx` 文件。
- 文件名建议格式：`原文件名-格式检查批注.docx`。
- 页面报告中提供下载按钮。

### 9.2 批注位置

批注应尽量插入到问题所在的真实位置：

- 字体、字号问题：批注插入到对应文本运行或所在段落。
- 段前、段后、行距、缩进问题：批注插入到对应段落。
- 表格问题：批注插入到对应表格或表格内第一个相关单元格。
- 大空白问题：批注插入到空白开始处的段落、分页符附近或异常空段落附近。

如果某类问题无法精确定位到单个字符，初版可以定位到所在段落或表格，并在批注中说明具体问题。

### 9.3 批注内容格式

批注内容建议统一格式：

```text
【F-001 错误】字体不符合模板
位置：第 3 页，第 12 段，正文
模板要求：宋体，小四
实际情况：微软雅黑，小四
修改建议：选中本段文字，将中文字体改为“宋体”，字号改为“小四”。
```

如果同一段落存在多个问题，批注内容应拆成编号列表：

```text
【S-003 错误】段落格式不符合模板
位置：第 4 页，第 8 段，关键词

1. 首行缩进不正确
模板要求：无首行缩进
实际情况：首行缩进 24 磅
修改建议：打开“段落”设置，将特殊格式改为“无”。

2. 行距不正确
模板要求：固定值 18 磅
实际情况：1.5 倍行距
修改建议：将行距改为“固定值”，设置值为 18 磅。
```

批注必须尽量避免只有“错误”两个字，而要给出可操作的修改方法。

系统实际生成批注时，应优先采用更口语化、更清楚的分行格式：

```text
问题编号：F-001
问题：字体与模板不一致
位置：第 3 段
应该这样：宋体
现在是：黑体
修改办法：选中第 3 段文字，将字体改为模板常用字体。
```

批注里不要直接暴露内部字段名或只有机器编号。编号用于和页面报告、HTML 报告互相查找，但正文必须让普通 Word 用户能看懂。

每个检测问题应生成一条独立 Word 批注，即使同一段中有多个问题也不合并。批注编号按类别重新计数，例如 `F-001`、`S-001`、`P-001`，每份报告从 001 开始。

全局但有对应区域的问题，例如目录和页码无法检查，应优先批注在目录区域附近；如果识别不到目录，则批注在文档开头。

### 9.4 批注作者

系统插入的批注作者统一为：

```text
Word格式检查系统
```

### 9.5 回写实现策略

使用 Open XML SDK 修改待检查文档副本：

- 打开目标 `.docx` 副本。
- 确保文档存在 `WordprocessingCommentsPart`。
- 为每个问题生成唯一批注 ID。
- 在问题位置插入 `CommentRangeStart`、`CommentRangeEnd` 和 `CommentReference`。
- 将批注正文写入 comments.xml。
- 保存为新的 `.docx` 文件并返回给用户下载。

### 9.6 限制说明

- Word 批注必须依附到文档结构中的具体元素，视觉空白类问题可能只能定位到附近段落。
- 如果一个段落存在多个问题，可以插入多个批注，也可以合并为一个批注。初版建议合并同一段落内的多个问题，减少批注数量。
- 系统不得修改原文档正文内容，只能增加批注和必要的批注引用标记。

## 10. 页面设计

### 10.1 首页

首页直接提供上传和分析功能，不做营销页。界面采用简单的两步流程，不做复杂导航和复杂仪表盘。

页面区域：

1. 第一步：上传模板
   - 只显示模板文档上传区域。
   - 显示文件格式和大小提示。
   - 按钮文字为“分析模板”。

2. 模板分析结果
   - 显示模板文件名。
   - 显示模板批注数量。
   - 显示识别到的主要格式摘要。
   - 如模板分析失败，显示错误原因，不进入第二步。

3. 第二步：上传实际文档
   - 只有模板分析成功后才显示。
   - 显示待检查文档上传区域。
   - 按钮文字为“开始检测”。

4. 检测完成后
   - 显示报告摘要。
   - 显示问题列表。
   - 提供带批注 Word 文档下载。
   - 提供 HTML 报告导出入口。

### 10.2 报告页

报告页保持简单，优先让用户看懂问题和下载结果。初版展示：

- 顶部摘要。
- 检测说明。
- 检测结论。
- 问题类型统计。
- 下载和导出操作区。
- 简单筛选区。
- 详细问题表格。

筛选条件：

- 问题类型。
- 严重级别。
- 只看错误。
- 下载带批注的 Word 文档。
- 导出 HTML 报告。

模板批注列表和模板规则摘要可以折叠显示，避免页面一开始过于复杂。

## 13. 对比规则设计

### 13.1 模板规则来源优先级

1. 模板批注中明确描述的规则。
2. 模板 Word 样式定义。
3. 模板正文中出现频率最高的格式。
4. 模板中相同位置或相同结构的格式。

初版建议先实现第 2、3、4 项。第 1 项先展示批注，后续再做自然语言规则解析。

### 13.2 容差规则

部分格式存在合理差异，需要允许容差：

- 字号必须完全一致。
- 字体必须完全一致。
- 段前段后间距允许少量差异。
- 行距允许少量差异。
- 表格列数原则上必须一致。

具体容差可在配置文件中维护。

## 14. 实现阶段

### 阶段 1：文档与项目骨架

- 完成本文档。
- 创建 ASP.NET Core Razor Pages 项目。
- 引入 Open XML SDK。
- 确认项目可以运行。

### 阶段 2：Word 读取能力

- 实现模板 `.docx` 文件上传。
- 读取模板批注。
- 提取段落、文本、表格基础信息。
- 在页面展示模板分析结果。
- 模板分析成功后，再显示实际文档上传入口。

### 阶段 3：格式对比能力

- 上传目标文档。
- 执行字体、字号、段落、表格、页面设置对比。
- 输出问题报告。

### 阶段 4：批注回写能力

- 根据问题定位信息找到目标文档中的段落、文本运行或表格。
- 在目标文档副本中插入 Word 批注。
- 页面提供带批注 Word 文档下载。
- 确认原始上传文件不被覆盖。

### 阶段 5：大空白检测

- 检测连续空段落。
- 检测异常段前段后间距。
- 检测连续分页符。
- 检测大量手动换行。

### 阶段 6：报告优化

- 增加问题筛选。
- 增加问题统计。
- 支持导出 HTML 报告。
- 后续支持导出 CSV 或 Excel。

### 阶段 7：批注语言与自动修正

- 将 Word 批注和页面报告改成普通用户能理解的自然语言。
- 补充标点符号检测，包括中文/英文标点、全角/半角标点、英文标点后空格。
- 提供“仅批注”和“自动修正生成正常文档”两种输出模式。
- 根据模板规则自动生成一个更接近模板的正常文档。

### 阶段 7 输出边界

“正常文档”必须是一个新的 `.docx` 文件，不覆盖用户上传原文档。初版自动调整范围包括：

- 按模板常见规则统一正文段落字体和字号。
- 按模板常见规则统一段落对齐、段前段后、行距、首行缩进。
- 按模板页面设置同步页边距、页眉页脚边距、纸张大小和纸张方向。
- 对常见标点问题做安全修正，例如重复标点、中文前后的半角标点、英文标点后缺空格等。

初版不承诺完全理解所有自然语言模板批注，也不承诺复杂表格结构、目录页码和分页视觉效果能自动修到人工最终状态。遇到不能安全自动修正的问题，应保留在批注文档和报告中提醒用户人工确认。

增强后的正常文档生成要求：

- 尽量按模板全量修正格式，但不修改正文文字内容。
- 覆盖封面、目录、正文、表格、页眉页脚、页码、文本框、脚注、尾注。
- 目录页码能更新则自动更新；不能更新时给出清楚提示。
- 编号只有在上下不一致时才自动修正，未出现编号时不新增。
- 原文档已有批注在正常文档中删除，输出干净最终稿，不保留修订痕迹。
- 无法安全自动修正的内容保留原样，只进入报告和必要批注。
- 自动修正记录只写入 HTML 报告，不写进正常 Word 文档。

### 阶段 8：精细格式引擎与覆盖率

- 建立 Word 术语转换层：字体、字号、段落、页边距、表格、图片、文本框、脚注、尾注等都优先显示 Word 用户能理解的名称。
- 字号显示应统一为 Word 术语，例如“小初”“小二”“小三”“小四”；无法识别时才显示原始值。
- 实现直接格式 + 样式继承链解析，避免出现不必要的“未设置”。
- 实现字符级、运行级、段落级和对象级检查，最终按用户可读方式展示。
- 检查范围覆盖正文、封面、摘要、目录、参考文献、附录、表格、页眉页脚、文本框、脚注、尾注。
- 增加覆盖率统计：字符数、段落数、对象数，按区域展示。
- 对未检查项给出原因，并写入页面、HTML 和必要的 Word 批注。

### 阶段 9：多模板规则冲突与规则确认

- 支持上传总模板后继续上传多个已合格参考模板。
- 比较总模板和参考模板的规则差异。
- 出现冲突时弹出规则冲突对话框。
- 用户可选择总模板规则、参考模板规则，或手动编辑规则。
- 用户确认后的规则用于当前检测和正常文档生成。
- 无法识别的模板批注标记为待确认，用户可以通过问题详情弹窗编辑。
- 确认后的规则只重新检查相关区域。

### 阶段 10：后台任务与正常文档增强

- 检查流程改为后台任务，显示百分比、当前区域和已发现问题数。
- 完成后自动刷新并弹出完成提示。
- 正常文档尽量按模板全量修正，但不改正文内容。
- 正常文档删除原批注，输出干净最终稿，不保留修订痕迹。
- 自动修正记录只写入 HTML 报告，按文档区域分组。
- 自动修正记录包含位置、修改项、修改前后、修改原因和模板规则摘要。
- 支持目录自动更新；不能更新时给出清楚提示。
- 支持表格跨页拆续表、重复表头。
- 支持图片因空白问题产生的等比缩放。

## 15. 初版验收标准

- 可以上传一个模板 `.docx`。
- 可以读取并显示模板中的批注。
- 模板分析完成前，不显示实际文档上传入口。
- 可以上传一个待检查 `.docx`。
- 可以输出字体、字号、段落间距、页面设置、表格结构、大空白相关问题。
- 页面能清楚显示问题位置、模板要求、实际情况和修改建议。
- 页面报告包含检测说明、检测结论、问题总数和问题分类统计。
- 页面报告可以按严重级别和问题类型筛选。
- 检测到问题后，可以下载一份带批注的 Word 文档。
- 可以根据模板规则生成一个正常文档。
- 可选择仅输出批注文档，或输出自动修正后的正常文档。
- 如实现 HTML 导出，导出的 HTML 报告可以离线打开，且与 Word 批注编号一致。
- 批注应出现在问题所在段落、文本或表格附近。
- 批注内容必须比参考样例更易读，使用自然语言，包含问题编号、位置、模板要求、实际情况和修改建议。
- 标点问题必须被检测出来并在报告和批注中说明。
- 系统生成的是新文件，不覆盖用户上传的原文件。
- 错误文件类型会给出明确提示。
- 项目可以通过 `dotnet build`。
- 项目可以通过 `dotnet run` 启动并在浏览器访问。

## 16. 风险与限制

- Open XML SDK 读取的是 Word 文件结构，不是真实视觉渲染结果。
- 大空白检测初版只能做结构化推断，不能等同于人工看到的页面空白。
- Word 样式继承较复杂，初版需要覆盖常见直接格式和常见样式，复杂样式链可逐步增强。
- 模板批注如果是自然语言，初版只展示，不自动理解全部规则。
- 批注回写依赖问题定位信息，部分复杂格式问题只能标记到段落或表格级别。
- 目录页码与实际页码完全比对依赖 Word 字段更新和页码渲染，初版可能只能做基础检测。
- 如果要达到接近人工视觉检查效果，后续需要增加 Word/PDF 渲染或版面识别能力。
